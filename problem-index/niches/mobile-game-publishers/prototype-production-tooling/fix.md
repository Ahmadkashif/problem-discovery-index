# Three Days of the Three Weeks Went on Plumbing

**Niche:** [[niches/mobile-game-publishers/prototype-production-tooling/profile|Prototype Production Tooling]]
**Industry:** [[industries/mobile-game-publishers|Mobile Game Publishers]]
**Type:** Fix (Pain Point)
**One-liner:** A three-week prototype cycle spends the first days on analytics, onboarding and build configuration that every other concept also needed.
**Tags:** #quick-win #workflow-orchestration #automation #data-integration #descriptive-statistics #evaluation-metrics #worker-facing #optimization-fundamentals
**Contested on:** Every serious competitor in this niche is fighting to cut the cost and time of getting a testable prototype in front of a paid audience, because the funnel's economics are set by that number — and whoever cuts it takes the account.

## The Problem
Ask a prototype team where the three weeks went and a consistent answer emerges: some days at the start on setup, some at the end on build, submission and campaign, and the middle on the actual concept. The setup work is the same every time and differs between teams only in which version of it they copied. It is the cheapest recoverable time in the business and nobody has counted it.

## Why It's Still Broken
Nobody measures where prototype time goes — work that is spread thinly across dozens of small cycles never appears as a number anyone is accountable for, so it is never targeted. Each team's copy diverges. Improving it competes with making games. And the fix is unglamorous.

## What a Fix Looks Like
Count it first, then delete it. Measure where prototype cycle time actually goes across teams, which is the fix's prerequisite and usually produces a larger number than anyone expected. Take the best existing team's setup and make it the shared default rather than designing something new, since the fastest improvement is already in the building. Automate build and submission, as that is a self-contained chunk of pure waiting. Pre-provision the test campaign so it is ready when the build is. Standardise the analytics event set, which removes setup work and produces comparability as a side effect. Retire the divergent copies deliberately rather than hoping teams migrate. Publish cycle time per prototype so the improvement is visible and stays. Keep one person accountable for it, because shared ownership here means none. Refresh the default quarterly from whatever teams have improved. And leave teams free to deviate, since a mandate produces workarounds rather than adoption.

## Who Feels the Pain
Prototype teams spending days on plumbing; engineering leads watching the same work repeated; publishers testing fewer concepts than their budget allows; and the concepts that never got built.

## Impact If Fixed
Work spread thinly across dozens of small cycles never appears as a number anyone is accountable for, so it is never targeted. Measuring cycle time and promoting the best existing setup to a shared default is the cheapest capacity in the business.
