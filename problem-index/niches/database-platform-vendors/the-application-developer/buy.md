**Contested on:** Every serious competitor that takes this seriously is fighting to tell a developer how a query will behave in production at the moment they write it — and whoever does that takes the developer, because the alternative is discovering it when the data grows and being blamed for it.

## The Problem
Several engines expose a what-if interface: given these statistics and these hypothetical indexes, what plan would you choose and at what cost. It exists to support physical design advisors. Query linting and static analysis tools exist for the common anti-patterns. Both are specialist tools used by specialists. The developer writing the query has neither, despite the analysis being cheap and the answer being available.

## What Already Exists
Hypothetical index and what-if optimiser interfaces in several engines; query linting and static analysis tools; SQL parsers with full coverage; schema-aware analysis; and code review integration frameworks. All available and mostly free.

## The Customization Gap
The adaptation is to a developer audience at write time. It requires: (1) production statistics available in development, which means exporting the statistics — a small, non-sensitive object containing distributions rather than data — and loading them into a local or hypothetical planner, and this is the piece nobody has packaged despite it being straightforward; (2) analysis of queries generated by frameworks rather than only of hand-written strings, since the majority of application queries are produced by an object-relational mapper at runtime and a linter that only sees literal SQL misses most of the estate; (3) output in terms a developer understands — this will scan the whole table, this will sort in memory, this will be slow when the table reaches this size — rather than a plan; (4) severity ranking and suppression, because a tool that warns on everything is ignored, which is the same lesson the security scanning ecosystem learned; and (5) growth projection, since the useful warning is about the future rather than the present and requires joining the schema analysis to the observed growth rate.

## Target Customer
Database and developer tooling vendors, framework and object-relational mapper projects, platform engineering teams, and the code review tooling ecosystem.

## Impact If Solved
The engine will answer the question hypothetically and the statistics are exportable, which leaves packaging and delivery as the entire gap. Analysing framework-generated queries is the adaptation that reaches where most application queries actually come from.
