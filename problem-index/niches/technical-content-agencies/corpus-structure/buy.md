## The Problem
The structured web solved machine-readable meaning with shared vocabularies: a page can declare that this is a product, this is a price, this is a review, this is a recipe step, and machines consume it reliably. Adoption was driven by search engines rewarding it. Technical documentation — which contains highly structured facts about versions, parameters, prerequisites and deprecations — marks up headings and code blocks and expresses the rest in prose.

## What Already Exists
Shared vocabularies for common entity types; embedded markup formats; validation tooling; consumption by search and assistant systems; and adoption incentives through improved presentation.

## The Customization Gap
The adaptation is to technical facts with no existing vocabulary. It requires: (1) a vocabulary for the things documentation actually asserts — version applicability, deprecation status, prerequisite relationships, parameter constraints — which does not exist and must be defined, and that definition is the substantive work; (2) authors writing in lightweight markup who will not hand-annotate, so the markup must be generated or inferred; (3) no adoption incentive equivalent to search ranking, so the benefit must be demonstrated; (4) facts that change with every release, so the markup must be generated from a source of truth rather than maintained; and (5) consumers whose use of the markup is not guaranteed or observable.

## Target Customer
Documentation teams and agencies, documentation platform vendors, standards bodies, and developer tooling providers.

## Impact If Solved
The structured web made machine-readable meaning standard because search rewarded it. A vocabulary for version applicability, deprecation and prerequisites does not exist and defining it is the substantive work.
