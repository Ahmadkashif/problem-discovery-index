# The Pull Request Waiting Two Weeks

**Niche:** [[niches/technical-content-agencies/engineering-review/profile|Engineering Review Dependency]]
**Industry:** [[industries/technical-content-agencies|Technical Content Agencies]]
**Type:** Fix (Pain Point)
**One-liner:** The documentation change has been awaiting a technical review since the feature shipped.
**Tags:** #quick-win #workflow-orchestration #automation #evaluation-metrics #descriptive-statistics #worker-facing #compliance #data-integration
**Contested on:** Every serious competitor in this niche is fighting to get a technical detail confirmed by an engineer whose sprint commitment does not include documentation review — and whoever unblocks that takes the account.

## The Problem
Documentation for a shipped feature sits in review while the feature is live and undocumented. The writer chases periodically. The engineer intends to get to it. Meanwhile users encounter a feature with no documentation, support answers questions the page would have answered, and the writer's work is complete and invisible. This is the ordinary state of documentation pipelines rather than an exception.

## Why It's Still Broken
There is no deadline on the review — a request with no due date and no consequence competes against work that has both and loses every time. Documentation is not part of the definition of done. Chasing is the writer's only lever. And nobody counts the waiting.

## What a Fix Looks Like
Make documentation part of shipping and shorten the ask. Include documentation review in the feature's definition of done, which is the fix and is a process decision rather than a tool. Ask a specific question with a proposed answer rather than requesting a general review, which turns a reading task into a confirmation. Route to the individual who wrote the code rather than to the team channel. Set a turnaround expectation and escalate on it, which requires leadership backing to mean anything. Ship with an unverified marker when the review does not arrive, rather than holding the page indefinitely. Measure how long documentation waits and report it alongside delivery metrics, since that is the number that gets it prioritised. Verify mechanically whatever can be verified so the human question is genuinely small. Batch reviews weekly with the team rather than individually, which several teams find easier. Recognise review in the engineer's own performance context. And treat a feature shipped without documentation as incomplete rather than as documented later.

## Who Feels the Pain
Writers whose finished work sits unpublished; users of an undocumented live feature; support teams answering questions the page would have answered; and engineers who intended to review and are now chased.

## Impact If Fixed
A request with no due date and no consequence competes against work that has both and loses every time. Putting documentation in the definition of done, with a one-minute specific ask, changes both sides.
