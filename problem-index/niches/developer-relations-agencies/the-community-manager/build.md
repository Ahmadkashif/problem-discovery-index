# Support Tooling for a Community Channel

**Industry:** [[industries/developer-relations-agencies|Developer Relations Agencies]]
**Type:** Build (Greenfield Opportunity)

**Contested on:** Every serious competitor in this niche is fighting to support the person running an unofficial support desk with no support tooling and no ticket queue — and whoever equips them takes the account.

## The Problem
Questions arrive in a community channel continuously, in no order, interleaved with conversation. There is no queue, so tracking what is outstanding is a memory task. There is no routing, so reaching someone who can answer is a personal request. There is no knowledge base, so the same question is answered repeatedly from scratch. The community manager does all of it, at volume, while also doing community management.

## Why Nobody Has Built This
Community platforms are built for conversation rather than for resolution. Support tooling assumes a ticket and a customer identity, neither of which exists here. The support function does not staff the community because it is not officially support. And the manager absorbing it means the volume never appears anywhere.

## What to Build
Give the channel the properties of a queue without making it a ticket system. Detect questions and track their state — open, answered, escalated — which is the core and replaces the memory task that defines the role. Route questions to people who can answer based on the topic, rather than relying on the manager to know and ask. Surface previous answers to the same question automatically, since a large share have been answered before in the same channel. Draft answers from the documentation for the manager to confirm, which is the leverage available for the routine majority. Escalate to support or engineering with a defined path, as the current escalation is a personal favour. Show what is outstanding and how long it has waited, which is invisible today. Preserve the conversational character of the channel, since making a community feel like a ticket system destroys what it is for. Measure the volume and the response times, so the load is visible to whoever staffs the role. Turn recurring questions into documentation rather than answering them indefinitely. And give the manager a boundary between community work and support work, which currently does not exist.

## Target Customer
Developer relations and community functions, community platform vendors, support operations, and community tooling providers.

## Impact If Built
The product's most visible support surface is run on a chat client and somebody's memory, and the volume appears nowhere. Question tracking with routing and answer reuse replaces the memory task the role is built on.
