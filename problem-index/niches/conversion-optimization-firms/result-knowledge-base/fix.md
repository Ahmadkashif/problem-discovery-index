# Testing Something That Was Tested Last Year

**Niche:** [[niches/conversion-optimization-firms/result-knowledge-base/profile|Result Reporting & Knowledge Base]]
**Industry:** [[industries/conversion-optimization-firms|Conversion Optimization Firms]]
**Type:** Fix (Pain Point)
**One-liner:** The test launching this week is one the programme ran eighteen months ago with a different strategist.
**Tags:** #quick-win #data-integration #descriptive-statistics #evaluation-metrics #workflow-orchestration #automation #word-embeddings #confidence-intervals
**Contested on:** Every serious competitor in this niche is fighting to keep what its tests established in a form anyone can retrieve, and whoever builds that record takes the account.

## The Problem
Programmes repeat tests. A strategist joins, proposes a reasonable hypothesis, and it is one that was tested two years ago on the same page with a clear result. Nobody knows, because the previous result is in a deck in a folder named after a month. The test consumes scarce capacity to establish something the programme already established, and it will be forgotten again.

## Why It's Still Broken
Results are stored by date — a record filed under the month it was reported cannot answer a question about a page or a hypothesis, so nobody consults it. There is no index. Strategists change. And repeating a test feels like fresh thinking.

## What a Fix Looks Like
Build a simple index and check it before launching. Maintain a one-line record per test — page, change, result, date — which is the fix and is a spreadsheet that takes minutes per test. Index by page and by change type, since those are what a strategist searches on. Check the index before adding anything to the backlog, as a mandatory step. Record null results as prominently as wins, which is where most of the useful prior information is. Backfill the last year from the existing decks, which is a day and immediately useful. Note the effect size and interval, so the record informs future power calculations. Record whether the winner was implemented, since a repeat is sometimes justified if the first was never shipped. Share it across the team rather than per strategist. Review it when onboarding someone new, which is when the repeats mostly originate. And keep it short, because a rich record nobody maintains is worse than a thin one that is current.

## Who Feels the Pain
Clients paying to establish something twice; strategists proposing tests the programme has answered; the test capacity, spent on known ground; and the programme's value, which should compound and does not.

## Impact If Fixed
A record filed under the month it was reported cannot answer a question about a page or a hypothesis, so nobody consults it. A one-line indexed record per test is minutes of work against repeated capacity.
