# External & Partner API Programmes

**Parent Industry:** [[industries/api-infrastructure-providers|API Infrastructure Providers]]
**Category:** Contested Sub-Niche
**Contested on:** Every serious competitor here is fighting to get an outside developer from first contact to a working production integration in the shortest possible time — and whoever does that takes the API programme, because time-to-first-call determines whether the programme has consumers at all.

## Profile
**Market Size:** ~$680M US external API programme infrastructure and monetisation
**Share of Parent Industry:** ~17% of category revenue
**Digital Adoption:** Medium — portals are universal and sandboxes are poor
**Target Buyer:** API product management, with adoption and revenue targets
**Automation Potential:** High — onboarding friction is measurable and mostly unmeasured

## What Makes This a Distinct Niche
An external API programme is a product with a funnel, and it is run by people who mostly do not think of it that way. A developer discovers the API, reads the documentation, obtains a key, makes a first call, builds an integration, ships it and generates revenue — and each of those steps loses a share of them, for reasons that are specific, ordinary and almost never measured. The contest is the funnel: whoever gets a developer to a working production integration fastest wins, because an API programme's value is entirely determined by how many consumers actually reach production and how much they use. The competitors are other providers of the same capability, the option of building it in-house, and the developer simply giving up, which is the most common outcome and is invisible to everybody.

## Current Tools & Gaps
Developer portals with interactive documentation, key self-service, sandbox environments of variable quality, code generation from specifications, and usage analytics. The gaps: the funnel is not instrumented, so nobody knows where developers are lost; sandboxes differ from production in ways that are discovered after the integration is written, which is the single most common cause of late failure; documentation describes intent rather than behaviour; error responses are designed for machines rather than for the human debugging at midnight; and support for external developers is frequently worse than for internal ones despite those developers being the revenue.
