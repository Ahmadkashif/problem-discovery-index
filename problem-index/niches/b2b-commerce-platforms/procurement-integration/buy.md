# Integration Platform and Connector Practice

**Niche:** [[niches/b2b-commerce-platforms/procurement-integration/profile|Procurement Integration]]
**Industry:** [[industries/b2b-commerce-platforms|B2B Commerce Platforms]]
**Type:** Buy & Customize (Vertical Adaptation)
**One-liner:** Integration platforms built maintained connector libraries so that connecting two systems is configuration rather than a project, and procurement integration is a project.
**Tags:** #data-integration #automation #workflow-orchestration #evaluation-metrics #compliance #confidence-intervals #graph-theory #quick-win
**Contested on:** Every serious competitor in this niche is fighting to connect to a large customer's purchasing system in hours rather than weeks — and whoever does that takes the account, because the connection is the condition of the relationship and its cost decides which customers are worth having.

## The Problem
Connecting two systems that were not designed for each other is an industry, and its central insight was that the connector should be a maintained product rather than a project: a library covering thousands of applications, each connector maintained centrally as the target changes, with mapping expressed as configuration and testing built in. Procurement integration has a small number of target platforms, high per-connection value, and is delivered as a bespoke project each time.

## What Already Exists
Integration platforms with maintained connector libraries; data mapping and transformation tooling with reusable templates; schema registries and format validation; connection testing and certification frameworks; monitoring of running integrations with alerting; and the practice of maintaining a connector as the target changes.

## The Customization Gap
The adaptation is to a connection between two companies where the counterparty configures their own side. It requires: (1) a profile per target procurement platform maintained centrally, which is the connector-library pattern applied to a domain where the target count is small and the value per connection is high — exactly the conditions where the pattern pays best and it has not been applied; (2) customer-level configuration layered over the platform profile, since two customers on the same procurement platform still differ and the difference should be declarative; (3) catalogue generation as part of the connector, since the catalogue format is the largest per-customer work item and is generated by hand; (4) testing against a simulated counterparty, since the customer's availability is the schedule's critical path and a simulator built from the profile removes it; and (5) certification, so a connection is verified against the profile before go-live rather than in production.

## Target Customer
Distributors, platform vendors, procurement platform providers, and the integration platform vendors for whom this is an adjacent and unusually well-suited domain.

## Impact If Solved
The connector-library pattern pays best where targets are few and value per connection is high, which describes this domain exactly, and it has not been applied. Testing against a simulated counterparty removes the customer's schedule from the critical path.
