# Four Hundred Implementations as an Asset

**Niche:** [[niches/saas-implementation-partners/configuration-reuse/profile|Configuration Reuse]]
**Industry:** [[industries/saas-implementation-partners|SaaS Implementation Partners]]
**Type:** Build (Greenfield Opportunity)
**One-liner:** The firm's delivery history is its largest asset and is stored as slides and recollection.
**Tags:** #data-integration #workflow-orchestration #evaluation-metrics #k-means-clustering #automation #tacit-knowledge-ml #descriptive-statistics #revenue-impact
**Contested on:** Every serious competitor in this niche is fighting to stop rebuilding what the firm has already built hundreds of times, and whoever industrialises that reuse takes the account.

## The Problem
Each engagement produces requirements, a configuration, integrations, test scripts and documentation. All of it exists in the client's tenant and the partner's project folders. Across hundreds of engagements on the same platform, the overlap is enormous and unexploited: the same objects, the same workflows, the same approval structures, the same integration shapes, built again by a consultant who has no way to see what the firm did last time.

## Why Nobody Has Built This
The artefacts belong to clients and live in their tenants, which is assumed to prevent reuse more broadly than it actually does. Nobody has framed the delivery history as a dataset. Billable models reward rebuilding. And extraction across hundreds of engagements is real work nobody has funded.

## What to Build
Catalogue what has been built, abstract the recurring shapes, and maintain them as assets. Extract configuration metadata from past engagements into a comparable catalogue, which is the core and is the step everything else depends on. Abstract recurring configurations into patterns with the variations that occur, since the value is in the shape rather than in any one client's version. Build a route from a new engagement's requirements to the closest prior patterns, which is what actually saves the time. Maintain deployable accelerators for the highest-frequency patterns, with an owner and a release cadence. Handle client confidentiality by abstracting rather than by abandoning reuse, which is a contractual and technical question with a workable answer. Measure what proportion of each engagement is rebuilt rather than reused, which is the number that justifies all of it. Record which patterns were used and how they performed, so the catalogue improves. Update patterns as the platform releases, which is what stops them rotting. Make the catalogue usable by a consultant mid-engagement rather than at proposal time. And price engagements on the reuse rather than on the hours, which is the business model change the asset enables.

## Target Customer
SaaS implementation partners and systems integrators, delivery leadership, platform vendors with partner ecosystems, and knowledge and asset management vendors.

## Impact If Built
The overlap across hundreds of engagements is enormous and unexploited because nobody has framed the delivery history as a dataset. A configuration catalogue abstracted into maintained patterns is the largest recoverable cost in the business.
