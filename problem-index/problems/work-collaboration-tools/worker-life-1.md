# Project Manager Status Chasing

**Industry:** [[work-collaboration-tools|Work Collaboration Tools]]
**Type:** Worker Life Changing
**One-liner:** Project managers stop spending their week asking people what they typed into the tool and then typing a summary of it, because the tool can observe what happened.
**Tags:** #large-language-models #gradient-boosting #bert #transformers #evaluation-metrics #automation #workflow-orchestration #worker-facing

## The Problem
A project manager's week has a shape. Chase people for status updates. Attend or run standups where those updates are repeated verbally. Update the plan to reflect what was said. Write a status report summarising it. Escalate the things that are late. Repeat.

Almost none of this is the job they were hired for. Project management is anticipating risk, resolving dependencies, protecting the team from disruption and making the hard sequencing calls. Status collection is the administrative shell around it, and the shell has grown to fill the week.

The absurdity is that a work management platform was purchased precisely so that status would be visible without asking. It did not work, because the status field requires a human to update it, and updating it is unrewarded work for the person doing it. So the project manager asks, and the asking is itself resented by the people being asked, which sets up a low-grade adversarial dynamic across the whole team.

Status reports compound it. The same information is reformatted for a team channel, an executive summary, a portfolio review and a stakeholder email, each in a different shape, weekly.

## Why It Matters to the Worker
Project managers occupy a position with high accountability and low authority. They own the delivery date and do not control the people delivering. Spending the week collecting information rather than acting on it makes that position worse, because the time that could go into unblocking dependencies goes into documenting that they are blocked.

The chasing is also relationally expensive. Every request for an update is a small imposition, and doing it weekly across a team of fifteen makes the project manager the person everyone slightly dreads hearing from. That reputation is earned by the process, not the person.

And the reporting is visibly wasteful. Everyone in the status meeting has already read the update. The report goes to executives who skim the first line. The project manager knows this and produces it anyway.

## What a Solution Looks Like
Status assembled from activity rather than collected from people. What moved, what did not, what is waiting on what, drawn from the tools where the work actually happened — commits, documents, reviews, threads — with the project manager reviewing and correcting rather than compiling.

Reports generated in the several shapes stakeholders want from one underlying assembly, so the reformatting disappears entirely.

Escalation surfaced by evidence rather than by asking. A task with no activity for eleven days, a review open for nine, a dependency that has slipped twice — these are the things the project manager needs to act on and they should arrive as a list rather than be discovered in conversation.

And the individual-versus-work boundary must hold. The output should describe work items and dependencies, never individuals' activity levels, both because that is what is actually useful and because the alternative turns the project manager into a monitor, which is the fastest way to destroy the team relationship the role depends on.

## Impact If Solved
Project management capacity is spent on collecting and reformatting information that the tooling already holds. Returning it to anticipation and dependency resolution is the difference between a coordinator and the role the discipline actually describes — and it removes the weekly imposition that makes the function unpopular with the teams it serves.
