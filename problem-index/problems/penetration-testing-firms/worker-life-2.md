# The Engineer Handed Eighty Findings

**Industry:** [[penetration-testing-firms|Penetration Testing Firms]]
**Type:** Worker Life Changing
**One-liner:** The report arrives with eighty findings and severity ratings assigned without knowledge of the client's architecture, and one security engineer has to turn it into work other teams will actually do.

## The Problem
A penetration test report lands with the client's security team, frequently one or two people. Eighty findings across several severities, each needing to be understood, validated, prioritised against everything else already outstanding, translated into a ticket a product team will accept, and then chased.

The severities are assigned by testers who do not know the environment. A finding rated high may sit behind controls the tester could not see; a medium may be far more serious given what the affected system connects to. Re-prioritising against actual architecture and data sensitivity is the security engineer's job and it is done by hand, per finding.

Then the negotiation. Product teams have roadmaps, and a security finding competes with features. The engineer has to make the case per finding, to several teams, with limited authority, using a severity rating the team can reasonably dispute because it came from someone who did not know the system.

Recurrence is the demoralising part. The same finding classes return in the next test because the underlying cause — a framework default, a pattern in a shared library, a gap in a template — was never addressed, only the instances. Nobody tracks that, so the engineer repeats the same negotiation annually.

## Why It Matters to the Worker
This role is accountable for outcomes it cannot enforce, with a work item list generated by someone else and a remediation capacity owned by teams that do not report to them. That is a structurally weak position occupied permanently.

The volume is the immediate problem and the prioritisation is the real one. Everything cannot be fixed; deciding what actually matters requires architectural knowledge and risk judgement, and the report's severities are a poor starting point that the engineer must first undo.

The recurrence is what wears people down. Watching the same issues return each year, knowing the systemic cause, and being unable to get the systemic fix prioritised because it is larger than any individual finding — that is the specific frustration that drives security engineers out of these roles.

And the compliance framing can make it worse. Where the test exists to satisfy an audit, the pressure is to close findings rather than to reduce risk, and those are not the same activity.

## What a Solution Looks Like
Re-prioritise against the environment automatically. Reachability, authentication context, data sensitivity and existing compensating controls are knowable from the client's own asset and architecture data, and adjusting a tester's severity against them produces a ranking the engineer can defend and a product team can accept.

Cluster findings by cause. Eighty findings are usually a much smaller number of systemic issues — a framework default, a shared library, a missing template control — and reporting the cause with its instance count is what makes a systemic fix arguable. This single change addresses the recurrence problem directly.

Track remediation and recurrence over time. Which findings were fixed, how long they took, which returned and which class they belong to gives the engineer the evidence to argue for structural work, and gives the testing firm the outcome data it currently lacks entirely.

Generate the tickets in the receiving team's terms. A finding translated into the affected repository, the specific code or configuration, and the change required is a ticket a product team will act on; a finding described in security language is a debate.

## Impact If Solved
The client-side security engineer is where testing turns into outcomes or does not, and they are handed a prioritisation built without knowledge of their environment. Environment-aware re-prioritisation, cause clustering and recurrence tracking would change which work gets done and would make the systemic fixes arguable for the first time — which is the difference between an annual test that finds the same things and a programme that reduces risk.
